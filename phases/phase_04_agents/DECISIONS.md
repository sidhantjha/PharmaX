# Phase 4A boundary decisions

- Feature code, typed request/task/finding/result schemas and tests remain local to Phase 4A. Schema `4a.1` is an additive JSON consumer boundary; no producer, shared contract or earlier dataset changes. `pyproject.toml` only registers the new tests.
- Reuse the archived H-MEM bridge pattern and the byte-identical official reference at `1742dec56a66e58eef9dda2d2b865823758ca8cd`. Vendor the unmodified reference, license, specification and official conformance vectors/runner under this phase. This is the actual engine, using deterministic hash embeddings and JSON persistence, not a production memory server.
- Partition persistent memory by session ID, dataset hash, mode and exact evidence cutoff. Physical partitioning supplements H-MEM's chat scope (which permits unscoped records). Reject unknown sources, unknown evidence, future revisions and unavailable parents before writes and after retrieval. The reference clock uses the evidence cutoff for deterministic ranking; it is **not** claimed as the real execution time. Terminal `completed_at` records execution time separately.
- Source IDs and evidence IDs are distinct: findings carry the source registry names, immutable evidence IDs and deterministic calculation hashes. The output includes the cited evidence closure and URLs. Local raw references are omitted. Derived findings can depend on simulations; hospital limitations explicitly say so.
- Preserve contradictory same-key values as separate H-MEM records and append `conflict_detected` ledger entries. Do not automatically resolve them. Use typed claim keys to avoid interpreting different hospital/scenario numbers as contradictions. Numerical claim keys include facility, horizon and scenario; the dataset is part of the memory partition. No dream/sleep maintenance or physical action runs automatically.
- Use the official hybrid ranker with top five and an explicit threshold of zero for this tiny, scoped investigation workspace. Scores/confidence are retrieval heuristics, not calibrated probabilities. Idempotent identical writes do not create duplicates. Memory is local trusted runtime storage; it is not safe to expose the upstream store directly as a public API.
- Nemotron chooses a typed task plan and at most one typed targeted follow-up. Three specialist workers execute typed retrieval/calculation plans concurrently; they are not three separately billed LLM chats. Final findings are assembled from tool results, not model-invented quantities. The offline policy is explicitly labelled a fixture policy, never model reasoning.
- Live mode reads only existing immutable Zetaris views via the Phase 2 compiler. Compare fetched rows with the pinned cache before calculating against it; mismatches and service failures fail closed. Cached mode uses the same records without network. Fixture mode forbids model clients and credentials. The inherited Phase 2 fixture lacks comparable trade query metadata: report unavailable rather than altering it or switching datasets.
- Reserve at most 24 tools (configurable 1..30), two model POSTs, 300 output tokens/32 KB response per POST, 24 KB serialized decision context, 250 KB per data/calculation response, ten seconds per memory subprocess. No automatic retries/fallback. Tasks share a 45-second dispatch deadline; read transport timeouts are at most ten seconds per request. A timed-out in-flight read cannot be killed by Python threads, but its result is ignored and no subsequent tool dispatch/memory write is permitted from that worker. This is a bounded read-only pilot, not a sandbox for arbitrary user code.
- No source acquisition, mitigation optimization, substitution, transfers, emails, orders, final report generation, frontend work, merge or deployment is authorized here. Unknown denominators, historical availability and manufacturing links remain explicit gaps even when a bounded investigation completes.
